# ADR-0010: What "best model" means (selection metric)

- **Status:** ACCEPTED
- **Date:** 2026-10-11
- **Decider:** Rex
- **Phase:** 1

## Context

ADR-0006 promises that a model is promoted only if it beats the current
champion, but not by which number. Run 507b2b3d showed the risk of choosing
badly: accuracy 0.6209 lost to a model that never reads the text (0.7181,
always guess the biggest class), while macro-F1 was 0.4638. The classes are
heavily imbalanced (about 368 to 1), and some mistakes are far more costly than
others: a missed urgent complaint (fraud, a consumer in a protected group, a
response deadline) costs much more than an extra review.

Recall rewards finding real cases; precision keeps the review queue workable.
Per-class cutoffs can trade one for the other after training without
retraining. The decision is cheap to change as a computation but load-bearing
once champion/challenger uses it as a promotion gate. It applies to the
`Product` routing task; a separate urgent-case flag (e.g. from `Tags`) is a
different target and is not decided here.

## Options considered

### Option A — Macro-F1 (the current number)
- Pros: balanced across classes; already logged.
- Cons: treats precision and recall equally, so it cannot express that misses
  cost more; in the lab it barely noticed critical-class recall changing.

### Option B — Macro-recall alone
- Pros: simple; cares about misses.
- Cons: trivially gamed by over-flagging (recall 99% with an 8.6x queue).

### Option C — Macro-F2 to rank, per-class recall floors as gates, plus a review-queue budget
- Pros: matches the asymmetric costs; floors stop an average hiding one
  collapsed class; the budget stops floors demanding an unstaffable queue.
- Cons: most to build; needs critical classes, floors and a budget chosen.

## Decision

Option C. Rank candidate models by macro-F2. A candidate is eligible only if
every critical class meets its recall floor and the critical-class review queue
stays within the budget. Critical classes, floors and the budget are kept in a
config file, not in code.

Provisional assumption (no domain owner available): the critical shortlist is
Debt or credit management, Payday/personal loan, Prepaid card and Money
transfer, chosen from data-derived harm signals (share tagged Older American or
Servicemember, untimely responses, ended in relief). Numeric floors and the
budget are NOT fixed here: they are set after baseline v2, from the model's
real precision-recall curves, because the lab's curves are simulated.

## Why

> Rex's own words.

we want such thresholds that the output generated by models satisfy the actual task of the model rather than the user - we don't want to just ignore the fact that it will definitely be underconfident while predicting classes it has seen less and we cannot ignore those classes as they are important for customer satisfaction too. We just need a floor which if crossed is a good enough value for the model to be used to those cases.

On adding the queue budget: Because we want a sweet spot between Macro F2 and queue size.

## Consequences

- Each run now logs `f2_macro` and `diagnostics/pr_curves.json` (per-class
  threshold, precision and recall at recall levels 0 to 1), so a floor can be
  turned into a per-class cutoff and its queue cost read off directly.
- Thresholds must be tuned on a validation split, not the test set. We have
  only train/test today, so a validation split is a pending decision.
- Gated classes sit at the strictest cutoff that still meets their floor; a
  class whose floor costs an absurd queue (Debt or credit management in the
  lab) signals a model/data problem, not a reason to accept the queue.
- The champion/challenger logic (ADR-0006 gap) will implement this rule.
- Revisit the critical list when a domain owner reviews it, and whenever the
  taxonomy or complaint mix shifts.
